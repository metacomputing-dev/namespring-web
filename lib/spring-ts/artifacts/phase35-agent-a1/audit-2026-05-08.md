## 3. Counting methodology — per-paragraph, not per-cell

`measure_p23.mjs:283-292` defines:

```js
const gyeolCnt = countMatches(ptext, /결/g);
if (gyeolCnt >= 3) {
  gyeolClusterCells.push({  // <-- variable misleadingly named "Cells"
    fixture: fixtureId, period: periodKey, category: catKey,
    tier, gyeolCount: gyeolCnt,
  });
}
```

The push happens **per paragraph** (inside the inner paragraphs
loop), so `gyeolClusterCells.length = 10` actually counts 10
**paragraphs** (one of which may live in the same cell as another).
The variable name "Cells" is historical drift; the actual semantics
are per-paragraph.

**Decision**: this gate uses **per-paragraph** semantics (matching
`measure_p23.mjs`) so the `--max-violations=10` threshold tracks
the documented baseline exactly. This differs from
`tools/check_flow_cluster.mjs` which uses per-cell dedup
(`hitOnceForCell`); we keep per-paragraph here to preserve the
Phase 23-34 measurement continuity.

The 10 paragraphs split by tier:
- **9 standard paragraphs** (8 are the same `한 달의 작은 결산은…` wealth fragment instance in 8 fixtures, 1 is a distinct `오전 한 시간만이라도…` career fragment instance variant; full enumeration below)
