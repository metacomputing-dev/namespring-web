## Issue (P22-A6 first-run trap)

`artifacts/phase22-agent-a5/measure_p22.mjs` invokes
`artifacts/phase12-agent-a5/extract-prose.mjs` to refresh
`prose-corpus.json` before running `audit-phase12.mjs` for the
`depth_inversion` passthrough. Pre-fix logic at `measure_p22.mjs:530`:

```js
const corpusPath = path.join(
  SPRING_TS_ROOT,
  'artifacts/phase12-agent-a5/prose-corpus.json',
);
if (!fs.existsSync(corpusPath)) {
  // run extract-prose.mjs
}
```

The `if (!fs.existsSync(corpusPath))` guard short-circuits whenever
the corpus file already exists, even if the file is stale relative to
the sample fixtures it's supposed to mirror.

### Real-world failure mode

P22-A6's workflow:

1. `npm run samples:regen` rewrites all 36 phase-3 sample fixtures
   from the post-merge src/data state. New `mtime(SAMPLES_DIR/*.json)`
   for every file.
2. P22-A6 runs `node artifacts/phase22-agent-a5/measure_p22.mjs ...`.
3. `measure_p22.mjs` checks `fs.existsSync(corpusPath)` — the corpus
   file from a prior audit (P21-A2 / P22-A5) already exists, so the
   refresh is **skipped**.
4. `audit-phase12.mjs` runs with the stale `prose-corpus.json` (still
   reflecting pre-regen sample text).
5. Output JSON reports `depthInversion.hits = 18` — the pre-regen
   baseline. P22-A6 audit doc almost shipped this stale figure as
   the post-fix value.
6. P22-A6 manually re-ran `extract-prose.mjs`, then re-ran
   `audit-phase12.mjs`, getting the true post-regen `0`.

P22-A6 audit doc lines 207-216 flag this as Phase 23 follow-up
(§Rec #5).

### New corpus refresh algorithm

`measure_p23.mjs:478-548` (the carry-over patch block) replaces the
P22-A5 `if (!fs.existsSync(corpusPath))` guard with an mtime-aware
decision:

```js
function safeMtime(p) {
  try { return fs.statSync(p).mtimeMs; }
  catch { return null; }
}

const corpusMtime = safeMtime(corpusPath);
const extractScriptMtime = safeMtime(extractScript);
let maxSampleMtime = 0;
for (const file of sampleFiles) {
  const m = safeMtime(path.join(SAMPLES_DIR, file));
  if (m !== null && m > maxSampleMtime) maxSampleMtime = m;
}

function decideRefresh() {
  if (corpusMtime === null) return { refresh: true, reason: 'corpus-missing' };
  if (maxSampleMtime > corpusMtime) return { refresh: true, reason: 'samples-newer-than-corpus' };
  if (extractScriptMtime !== null && extractScriptMtime > corpusMtime) {
    return { refresh: true, reason: 'extract-script-newer-than-corpus' };
  }
  return { refresh: false, reason: 'corpus-fresh' };
}
```

Refresh fires when **any** of three conditions hold:

1. **Corpus missing** — same as the P22-A5 guard. Cold-start case.
2. **Samples newer than corpus** — the P22-A6 trap. After
   `samples:regen`, every sample file gets a fresh mtime; the
   `max(mtime(sample))` strictly exceeds the corpus's prior mtime.
3. **Extract-prose.mjs script newer than corpus** — defensive case.
   If the extractor itself is patched (record shape change, new
   walker, etc.), the corpus structure may be stale even if samples
   are unchanged. Refresh from the new extractor.

#### Why max-mtime over directory mtime

Windows directory `mtime` is unreliable for in-place file rewrites:
the directory inode does not always update when a file's content is
overwritten without a name change. `samples:regen` writes via
`fs.writeFileSync` to existing paths, so the directory mtime can lag.
Iterating every sample file and taking the max guarantees the check
sees the freshest content time on any platform.

### Output JSON addition (`corpusFreshness`)

`measure_p23.mjs` now emits a new top-level field:

```json
"corpusFreshness": {
  "corpusExisted": true,
  "corpusMtimeBefore": 1746605784573.3257,
  "maxSampleMtime": 1746609012345.123,
  "maxSampleMtimeFile": "01-..-tiered.json",
  "extractScriptMtime": 1746587000000.0,
  "refreshed": true,
  "reason": "samples-newer-than-corpus",
  "refreshError": null,
  "corpusMtimeAfter": 1746609055123.456,
  "notes": "P22-A6 §Rec #5 carry-over. ..."
}
```

This block makes the refresh decision auditable post-hoc. Future
agents reading the snapshot JSON can confirm:

- whether the corpus existed before this run;
- whether a refresh fired and why;
- whether the refresh succeeded (corpusMtimeAfter > corpusMtimeBefore
  when `refreshed === true`);
- which sample file is the freshest (sanity check that
  `samples:regen` actually wrote new content).

If P22-A6 had had this block, the stale 18 figure would have
self-flagged at JSON inspection time
(`refreshed: false, reason: 'corpus-fresh'` despite freshly-regen'd
samples — an immediate contradiction). The bug is now self-diagnostic
even if the algorithm somehow miscomputes.

## Before/after stale scenario

| Phase | Trigger | P22-A5 behavior | P23-A4 behavior |
|---|---|---|---|
| Cold start | corpus missing | Refresh fires (`fs.existsSync` false) | Refresh fires (`reason: 'corpus-missing'`) |
| Same-run repeat | corpus fresh from earlier in session | Skip (existsSync true) | Skip (`reason: 'corpus-fresh'`; corpus mtime ≥ max sample mtime) |
| **P22-A6 trap** — post `samples:regen` | corpus from prior phase, samples regenerated | **Skip — stale read of pre-regen prose** | **Refresh fires (`reason: 'samples-newer-than-corpus'`)** |
| Extractor patched | corpus from prior version, extract-prose.mjs edited | Skip — corpus shape may not match new audit reader | Refresh fires (`reason: 'extract-script-newer-than-corpus'`) |
| Manual delete | corpus removed | Refresh fires | Refresh fires (`reason: 'corpus-missing'`) |

The **P22-A6 trap row** is the bug; the rest are unchanged behavior.

  matched the on-disk samples, not a stale predecessor. The carry-over
